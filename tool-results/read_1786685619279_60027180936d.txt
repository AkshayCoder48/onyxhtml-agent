    56→- `src/lib/ai/agent.ts` — Agentic streaming loop:
    57→  - `runAgentAsReadableStream(options)` returns a `ReadableStream<Uint8Array>` that emits SSE chunks.
    58→  - SSE encoding: `data: <JSON>\n\n` per event, terminated by `data: [DONE]\n\n`.
    59→  - `sseResponse(stream)` sets headers `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, `Connection: keep-alive`, `X-Accel-Buffering: no`.
    60→  - `buildSystemPrompt(...)` includes the workspace name, entry file, a rendered file tree (📁/📄), the active file content (capped at 8 KB), selected files, and concise guidelines.
    61→  - `buildConversationFromMessages(systemPrompt, rows)` parses stored segments into OpenAI chat messages: user → `{role:"user", content}`; assistant → `{role:"assistant", content, tool_calls}` followed by one `{role:"tool", tool_call_id, content}` per tool_call segment (so the provider sees full tool history on resume).
    62→  - Loop control: cap at 8 rounds; each round streams from the provider, accumulates reasoning/content into segments (folding into the previous segment of the same type), accumulates tool_calls. After the stream ends:
    63→    - For each tool call: emit `{type:"tool_call", ...}` (with `status:"running"` for browser tools, no status for file tools — frontend reads `status`).
    64→    - File tools: execute server-side immediately, update the segment to success/error, emit `{type:"tool_result", ...}`, append a tool message to the conversation.
    65→    - Browser tools: push the segment in `running` status, accumulate `callId`s.
    66→    - Persist segments after each round.
    67→    - If any browser tools pending → emit `{type:"browser_tools_pending", callIds}` + `[DONE]`, close stream (resume via `/continue`).
    68→    - Else if file tools ran → loop again with updated conversation.
    69→    - Else (no tool calls) → emit `{type:"done"}` + `[DONE]`, close stream.
    70→    - On provider error → emit `{type:"error", content}` + `[DONE]`.
    71→  - `/continue` path: applies `resumeResults` to pending `tool_call` segments (status → success/error, sets result/error), emits a `tool_result` event for each, appends tool messages to the conversation, then re-enters the loop.
    72→  - `serializeMessage(row)` parses segments JSON for API responses.
    73→  - `maybeAutoTitle(chatId)` sets the chat title from the first ~40 chars of the first user message if it's still "New Chat".

   116→### AI streaming architecture summary
   117→
   118→1. Route handler (`POST /api/chats/[id]/messages`) creates a user Message and an empty assistant Message, calls `maybeAutoTitle`, then invokes `runAgentAsReadableStream({ chatId, workspaceId, context })` and returns `sseResponse(stream)`.
   119→2. `runAgentAsReadableStream` opens a `ReadableStream` and runs `runAgentLoop` inside `start(controller)`. The `send` helper enqueues SSE-encoded events; `sendDone` enqueues `[DONE]` and closes the controller.
   120→3. `runAgentLoop`:
   121→   a. Loads workspace + files, builds system prompt with file tree + active file.
   122→   b. Calls `getActiveProvider()` (seeds built-in if needed).
   123→   c. Loads chat messages and builds the OpenAI-format conversation (excluding the empty assistant message we're about to fill).
   124→   d. For `/continue`: applies `resumeResults` to pending `tool_call` segments and appends tool messages.
   125→   e. Enters the agentic loop (max 8 rounds):
   126→      - `streamChatCompletion(provider, { messages, tools })` yields `reasoning_content` / `content` / `tool_call_delta` / `error` events. Each delta is forwarded to the client and accumulated.
   127→      - On stream end, merges accumulated reasoning/content into segments, then processes tool calls:
   128→        - File tools → execute server-side via `executeFileTool`, emit `tool_call` + `tool_result`, append a tool message.
   129→        - Browser tools → emit `tool_call` with `status:"running"`, leave the segment pending.
   130→      - If browser tools pending → emit `browser_tools_pending` + `[DONE]` and return (resume via `/continue`).
   131→      - If only file tools ran → loop again.
   132→      - If no tool calls → emit `done` + `[DONE]`.
   133→4. Segments are persisted after every round so the assistant message reflects the latest state even if the connection drops.
   134→5. The `/continue` endpoint re-enters the loop with `resumeResults` — identical control flow, so it can produce more tool calls (including more browser tools) and pause again.

   142→### Deviations from spec
   143→
   144→- The `tool_call` event for browser tools includes a `status: "running"` field as the spec suggested (extending the `StreamEvent` type inline via `@ts-expect-error`). The frontend can read this to render a pending state. File-tool `tool_call` events omit `status` (they complete immediately).
   145→- `/api/workspaces/[id]/import` ignores the `[id]` path param and always creates a new workspace (the spec says "Create a new workspace named after the zip filename"). Kept the `[id]` segment in the URL to match the documented route shape; the route works regardless of the id passed.
   146→- Built-in provider's `/models` endpoint returns a hardcoded list of GLM-4 family models (the SDK doesn't expose `/models` directly). User-configured OpenAI-compatible providers fetch from `${baseURL}/models` as specified.
   147→- `search_files` matches across all files in one pass (no regex, just `String.includes`); returns up to 50 matches with `path`, `line` (1-based), `text` (trimmed, capped at 200 chars).
   148→- The `rename_file` tool and the `/files/rename` route both support renaming a single file or an entire folder (children with the `from + "/"` prefix are renamed transactionally).

   150→### Security

   152→- Every file path is validated with `safePath` (rejects `..`, absolute, Windows drive prefixes, leading slashes).
   153→- ZIP import rejects unsafe paths and OS metadata (`__MACOSX/`, `._*`, `.DS_Store`, `Thumbs.db`).

   257→### SSE handling approach
   258→
   259→`api.streamMessage(chatId, body, signal)` returns an async generator of `StreamEvent`. Internally it `fetch`es with POST, gets the `ReadableStream`, decodes with `TextDecoder`, splits the buffer on `\n\n`, parses lines starting with `data: `, ignores `data: [DONE]` (returns from the generator), and `JSON.parse`s everything else.
   260→
   261→`useChatStream.sendMessage(content)`:
   262→1. Appends a user Message and an empty assistant Message to the chat store.
   263→2. Calls `startStreaming(assistantId)`.
   264→3. Creates an `AbortController` and stores it on a ref.
   265→4. Iterates the async generator with `for await`, dispatching each event to `handleEvent`:
   266→   - `reasoning_content` → append to the last `thinking` segment (or push a new one).
   267→   - `content` → append to the last `content` segment.
   268→   - `tool_call` → `upsertToolCallSegment` by `callId` with `status: running`.
   269→   - `tool_result` → `setToolResult` updates the matching segment with `status`, `result`, `error`, `label`, `detail`.
   270→   - `error` → push an `error` segment.
   271→   - `done` → break the loop.
   272→   - `browser_tools_pending` (loose-typed payload with `callIds[]`) → collect callIds, set `pendingBrowserTools`.
   273→5. After the primary stream ends, if there are pending browser tools, call `executeBrowserToolsAndContinue`:
   274→   - For each callId, find the segment in the assistant message to get the tool name + args.
   275→   - Call `bridge.execute(tool, args, callId)` (postMessage to the iframe).
   276→   - Update the segment with the result via `setToolResult`.
   277→   - Collect results into `{callId, result?, error?}[]`.
   278→   - Call `api.streamContinue(chatId, {results}, signal)` and resume consuming the new stream (same `handleEvent` dispatch).
   279→6. On any error: push an error segment, toast with Retry action.
   280→7. Finally: `stopStreaming()` and clear the controller.
   281→
   282→### Preview bridge protocol
   283→
   284→`buildPreviewDoc` inlines local CSS / JS / SVG-image references into the entry HTML, then injects a bridge `<script>` before `</body>`. The bridge:
   285→
   286→- Wraps `console.log/warn/error/info` to forward each call to the parent as `{source:"preview", kind:"console", level, args}` (args are stringified safely).
   287→- Listens for `window.error` and `unhandledrejection` to forward `{source:"preview", kind:"error", message, filename, line, col}`.
   288→- Captures failed resource loads (LINK/SCRIPT/IMG) and forwards as `{source:"preview", kind:"network", url, type, status:0}`.
   289→- Listens for messages from the parent of the form `{source:"workspace-host", action:"browser-tool", tool, args, callId}`. Implements: `click`, `type`, `press_key`, `scroll`, `hover`, `select`, `get_dom`, `run_javascript` (via `eval`), `get_console_logs`, `get_page_errors`, `take_screenshot` (returns a not-supported note), `wait`. Posts back `{source:"preview", callId, result?, error?}`.
   290→
   291→The host (`usePreviewBridge`) keeps a `Map<callId, resolver>` and resolves when the matching reply arrives (8s timeout). The host's `message` listener also routes console/error/network posts to the ConsoleDrawer state.
