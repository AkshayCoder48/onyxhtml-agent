   257→### SSE handling approach
   258→
   259→`api.streamMessage(chatId, body, signal)` returns an async generator of `StreamEvent`. Internally it `fetch`es with POST, gets the `ReadableStream`, decodes with `TextDecoder`, splits the buffer on `\n\n`, parses lines starting with `data: `, ignores `data: [DONE]` (returns from the generator), and `JSON.parse`s everything else.
   260→
   261→`useChatStream.sendMessage(content)`:
   262→1. Appends a user Message and an empty assistant Message to the chat store.
   263→2. Calls `startStreaming(assistantId)`.
   264→3. Creates an `AbortController` and stores it on a ref.
   265→4. Iterates the async generator with `for await`, dispatching each event to `handleEvent`:
   266→   - `reasoning_content` → append to the last `thinking` segment (or push a new one).
   267→   - `content` → append to the last `content` segment.
   268→   - `tool_call` → `upsertToolCallSegment` by `callId` with `status: running`.
   269→   - `tool_result` → `setToolResult` updates the matching segment with `status`, `result`, `error`, `label`, `detail`.
   270→   - `error` → push an `error` segment.
   271→   - `done` → break the loop.
   272→   - `browser_tools_pending` (loose-typed payload with `callIds[]`) → collect callIds, set `pendingBrowserTools`.
   273→5. After the primary stream ends, if there are pending browser tools, call `executeBrowserToolsAndContinue`:
   274→   - For each callId, find the segment in the assistant message to get the tool name + args.
   275→   - Call `bridge.execute(tool, args, callId)` (postMessage to the iframe).
   276→   - Update the segment with the result via `setToolResult`.
   277→   - Collect results into `{callId, result?, error?}[]`.
   278→   - Call `api.streamContinue(chatId, {results}, signal)` and resume consuming the new stream (same `handleEvent` dispatch).
   279→6. On any error: push an error segment, toast with Retry action.
   280→7. Finally: `stopStreaming()` and clear the controller.
   281→
   282→### Preview bridge protocol
   283→
   284→`buildPreviewDoc` inlines local CSS / JS / SVG-image references into the entry HTML, then injects a bridge `<script>` before `</body>`. The bridge:
   285→
   286→- Wraps `console.log/warn/error/info` to forward each call to the parent as `{source:"preview", kind:"console", level, args}` (args are stringified safely).
   287→- Listens for `window.error` and `unhandledrejection` to forward `{source:"preview", kind:"error", message, filename, line, col}`.
   288→- Captures failed resource loads (LINK/SCRIPT/IMG) and forwards as `{source:"preview", kind:"network", url, type, status:0}`.
   289→- Listens for messages from the parent of the form `{source:"workspace-host", action:"browser-tool", tool, args, callId}`. Implements: `click`, `type`, `press_key`, `scroll`, `hover`, `select`, `get_dom`, `run_javascript` (via `eval`), `get_console_logs`, `get_page_errors`, `take_screenshot` (returns a not-supported note), `wait`. Posts back `{source:"preview", callId, result?, error?}`.
   290→
   291→The host (`usePreviewBridge`) keeps a `Map<callId, resolver>` and resolves when the matching reply arrives (8s timeout). The host's `message` listener also routes console/error/network posts to the ConsoleDrawer state.
