PRD — AI HTML Workspace Editor

1. Product Overview

Build a polished browser-based AI HTML Workspace Editor for creating, editing, previewing, testing, and downloading multi-file static websites through an AI coding agent.

The product combines:

- AI coding agent
- Multi-file HTML/CSS/JS editor
- Live website preview
- Browser automation/testing
- Console and error inspection
- AI reasoning/thinking panel
- Collapsible tool-call cards
- Chat history
- Workspace management
- OpenAI-compatible API configuration
- ZIP workspace export

The application should feel like a modern developer tool rather than a basic HTML playground.

The primary desktop experience uses a three-zone layout:

┌──────────────────────────────────────────────────────────────────────────┐
│ Sidebar │                 Workspace Header                               │
│         ├────────────────────────────────────┬───────────────────────────┤

The interface must have clear visual hierarchy and avoid overcrowding.

2. Design Direction

Visual style

Use a modern developer-tool aesthetic:

- Rounded cards
- Subtle borders
- Moderate corner radius
- Clean typography
- Compact controls
- Smooth transitions
- Minimal shadows
- Strong spacing hierarchy
- Dark and light appearance support
- Responsive behavior
- Keyboard accessibility

Do not make every element look like a floating card. Panels should primarily use borders and background separation.

Component hierarchy

Use three visual levels:

Level 1 — Application surfaces

Large areas such as:

- Sidebar
- Editor
- Preview
- Chat

Use subtle background differences and borders.

Level 2 — Interactive containers

Examples:

- File explorer
- Chat messages
- Thinking panel
- Tool cards
- Prompt box
- Settings sections

Use rounded corners and subtle borders.

Level 3 — Controls

Examples:

- Buttons
- Tabs
- Dropdowns
- Icon buttons
- Toggles

Keep these compact.

45. JavaScript Execution Security

"run_javascript" executes inside the preview context only.

It must not have automatic access to:

- Application API keys
- Authentication tokens
- Parent window privileged APIs
- Internal application state
- Workspace database
- Browser storage belonging to the main application

Use isolation such as a sandboxed iframe or equivalent secure preview environment.

48. Message Segment Model

Assistant messages must support structured segments.

segments:
[
  {
    type: "thinking",
    content: "..."
  },
  {
    type: "tool_call",
    tool: "read_file",
    arguments: {}
  },
  {
    type: "tool_result",
    result: {}
  },
  {
    type: "content",
    content: "..."
  }
]

This prevents reasoning, tools, and final responses from becoming one string.

   ↓
Build file tree
   ↓
Open project

71. Final Acceptance Criteria

The application is complete when:

Workspace

- Users can create workspaces.
- Users can import ZIP projects.
- Users can download complete workspaces.
- Multiple files and folders work correctly.
- Workspace state survives refreshes.

Editor

- HTML/CSS/JS editing works.
- Multiple tabs work.
- File explorer works.
- Unsaved state is visible.
- Autosave works.
- Errors are visible.

Preview

- Websites render correctly.
- Relative files work.
- Assets work.
- Responsive viewport controls work.
- Reload works.
- Console/errors/network inspection work.

AI

- AI can inspect workspace files.
- AI can modify files.
- AI can create/delete/rename files.
- AI can execute JavaScript in the preview.
- AI can click/type/scroll/interact with the website.
- AI can inspect DOM and errors.
- AI can test and fix issues iteratively.

Reasoning

- "reasoning_content" is parsed separately.
- Reasoning is displayed only inside the Thinking panel.
- Thinking streams correctly.
- Thinking is collapsible.
- Thinking collapses after completion.
- Empty reasoning does not create an empty panel.
- Reasoning is not mixed with normal content.
- Reasoning does not contain tool cards.
- Multiple reasoning segments are handled correctly.
- Provider-specific reasoning fields are normalized.

Tool calls

- Tool calls appear as compact cards.
- Cards support running/success/error/cancelled states.
- Cards can expand/collapse.
- Tool results do not appear as raw JSON by default.
- Existing cards update during streaming.
- Tool cards remain separate from Thinking.

Chat

- Chat history persists.
- Messages survive refreshes.
- Streaming works.
- Stop generation works.
- Retry works.
- Regeneration works.
- Search works.
- Prompt box remains accessible.

Providers

- OpenAI-compatible Base URL works.
- API key is optional.
- Manual model entry works.
- "/models" discovery works when available.
- Connection testing works.
- API keys are never exposed.

UI

- Every major action has a clear button.
- Icon-only buttons have tooltips.
- Primary/secondary/ghost/destructive buttons are visually distinct.
- Controls remain consistent across the application.
- Desktop uses the dual-panel workspace.
- Mobile uses Code/Preview/AI/Files navigation.
- Dark/light/system appearance works.
- Empty/loading/error states are implemented.
- No major panel feels visually overcrowded.

The final product should feel like a focused AI-native web development environment: the user describes what they want, the AI can inspect and modify the complete project, interact with the running website, test its behavior, show its available reasoning in a collapsible Thinking panel, expose its tool activity through compact cards, and leave the user with a downloadable, functioning static website.
